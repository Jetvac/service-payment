# VPN Payment Control

Веб-приложение для контроля равных оплат участников VPN-сервисов.

## Возможности

- сервисы с месячной стоимостью и валютой;
- закрепление участников за сервисами;
- расчёт доли участника за месяц, неделю, день и час;
- общий баланс участника в RUB для всех подключённых сервисов;
- списания могут уводить баланс участника в минус, показывая задолженность;
- денежные операции округляются и отображаются с точностью до 2 знаков;
- ручные пополнения без банка и подтверждаемые онлайн-платежи через ЮKassa (СБП и СберБанк Онлайн);
- ежемесячные автоплатежи участников с настраиваемым числом месяца и суммой;
- ручные и автоматические списания по календарному расписанию;
- отдельные журналы зачислений и списаний;
- отмена зачислений и списаний через корректирующую обратную операцию;
- Telegram webhook или polling для `/pay`, `/deposit`, `/balance`, `/services`, `/users`, `/help`;
- кнопки команд в личке Telegram и настройка бота из интерфейса;
- поддержка Telegram-топиков в группе через админ-команду `/settopic`;
- уведомления о низком остатке и общая сводка остатков после списания сервиса;
- единый SQLite-backup: настройки, операции, публикации, комментарии и содержимое загруженных файлов;
- безопасное обновление приложения из git через интерфейс с предварительной сборкой, backup, health-check и rollback.

## Хранение и резервное копирование

Основная база — `data/service-payment.sqlite`. Файлы стены и изображения сохраняются BLOB-объектами в этой же базе. При первом запуске существующий `data/db.json` и файлы из `data/wall-files` автоматически мигрируют; исходные файлы не удаляются.

SQLite не требует отдельного сервера или Docker. TimescaleDB, замеры пинга, графики задержки, настройки мониторинга и команда `/status` удалены. Старые поля мониторинга очищаются при открытии базы. Путь к данным можно изменить через `APP_DATA_DIR`, путь к SQLite — через `APP_DATABASE_PATH`.

В `Telegram → Система`:

- `Скачать БД` создаёт согласованную SQLite-копию, включая загруженные файлы;
- `Загрузить БД` проверяет целостность SQLite и наличие содержимого вложений; состояние и файлы заменяются одной транзакцией, при ошибке прежняя база остаётся на месте;
- копия включает участников, балансы, сервисы, подписки, зачисления, списания, оплаты, расписания, настройки и секреты, уведомления, посты, теги, комментарии и загруженные файлы;
- старый JSON-backup восстанавливает переданные разделы стены; отсутствующие в старом формате разделы сохраняются из текущей базы. Для вложений JSON нужны уже имеющиеся файлы с теми же идентификаторами, иначе импорт отклоняется;
- после восстановления потребуется повторный вход с паролем из копии.

Перед импортом рекомендуется скачать текущую БД. Если при экспорте обнаружено отсутствующее вложение, копия не выдаётся как полная. Лимит загрузки SQLite по умолчанию — 2 ГБ (`MAX_BACKUP_MB`); на существующем nginx установите соответствующий `client_max_body_size`, например `2048m`. Для новых установок скрипт уже задаёт этот лимит.

## Запуск

```bash
npm install
npm run dev
```

Клиент будет доступен на `http://localhost:5173`, API на `http://localhost:4077`.

## Production

```bash
npm run build
npm start
```

После сборки backend отдаёт готовый интерфейс на `http://localhost:4077`.

В разделе Telegram есть блок `Система`: кнопки `Скачать БД`, `Загрузить БД` и `Обновить приложение`. На Ubuntu обновление скачивает ветку GitHub во временный каталог, устанавливает зависимости и собирает кандидата вне работающего сайта. Только после успешной сборки оно заменяет код, перезапускает systemd и проверяет `/api/health`. При неуспешном health-check автоматически возвращается предыдущий релиз. Подробный лог: `data/logs/update.log`.

## Deploy на Ubuntu

В репозитории есть скрипт `scripts/deploy-ubuntu.sh`. Он устанавливает Node.js и системные зависимости для SQLite, клонирует или обновляет `Jetvac/service-payment`, собирает приложение, создаёт systemd-сервис и при необходимости настраивает nginx. Команда остаётся идемпотентной: существующий env-файл, пароль и данные повторным запуском не сбрасываются.

Минимальный запуск на сервере:

```bash
curl -fsSL https://raw.githubusercontent.com/Jetvac/service-payment/main/scripts/deploy-ubuntu.sh | sudo bash
```

С доменом и nginx:

```bash
curl -fsSL https://raw.githubusercontent.com/Jetvac/service-payment/main/scripts/deploy-ubuntu.sh | sudo env DOMAIN=pay.example.com bash
```

С HTTPS через Let's Encrypt:

```bash
curl -fsSL https://raw.githubusercontent.com/Jetvac/service-payment/main/scripts/deploy-ubuntu.sh | sudo env DOMAIN=pay.example.com ENABLE_SSL=true EMAIL=admin@example.com bash
```

Полезные переменные: `APP_DIR=/opt/service-payment`, `PORT=4077`, `BRANCH=main`, `ENABLE_UFW=true`. Сгенерированный начальный пароль администратора печатается в итогах установки и сохраняется в `/etc/service-payment.env`. После первого входа смените его в `Telegram → Система`.

## Обновление сервера

Если сервер уже развёрнут, обновить приложение можно без авторизации в GitHub через raw-скрипт:

```bash
curl -fsSL https://raw.githubusercontent.com/Jetvac/service-payment/main/scripts/update-ubuntu.sh | sudo env APP_DIR=/opt/service-payment APP_SERVICE_NAME=service-payment bash
```

Первый переход на версию без TimescaleDB выполните этой командой от root: старый локальный скрипт кнопки обновления ещё не умеет удалять контейнер. Команда должна скачивать уже опубликованную новую версию репозитория.

Скрипт сначала собирает кандидат во временном каталоге. Затем останавливает приложение, создаёт согласованную SQLite-копию, архив данных (включая старый JSON и внешние файлы) и копию env в `APP_DATA_DIR/backups/pre-update-<дата>-<pid>/`. Каталоги старых backup и логов в архив не включаются. Если база по настроенному пути отсутствует, обновление прерывается, чтобы не создать пустую базу вместо старой.

После замены кода проверяется миграция и полнота вложений, выполняется запуск и health-check. При ошибке миграции или запуска возвращаются прежние код и SQLite. Исходные JSON и внешние файлы сохраняются. Одновременное обновление блокируется.

Только после успешной проверки удаляются контейнер TimescaleDB этого приложения, его подключённый именованный том и неиспользуемый образ. Перед удалением сохраняется `legacy-postgres.sql` — страховочная копия на случай дополнительных таблиц в старой установке. Имена берутся из прежнего env (`TIMESCALE_CONTAINER_NAME`, `TIMESCALE_VOLUME`), по умолчанию — `service-payment-timescaledb` и `service-payment-timescaledb-data`. Чужие контейнеры и Docker не удаляются. Если очистка Docker не удалась, новая версия остаётся работающей; причина видна в логе, команду можно повторить. Удалённые echo-серверы на отдельных VPN-хостах автоматически не деинсталлируются.

После этого можно пользоваться `Telegram → Система → Обновить приложение`. Устанавливается отдельная systemd-служба `service-payment-update.service`, переживающая остановку сайта. Лог: `data/logs/update.log`, также доступен `systemctl status service-payment-update`. Для другого имени приложения имя службы меняется соответственно.

## Платежи

Слева доступен раздел `Внести оплату`. Пользователь выбирает сервис, сумму и способ:

- `Без банка` — немедленное ручное зачисление;
- `СБП` — redirect-сценарий ЮKassa;
- `СберБанк Онлайн` — redirect-сценарий ЮKassa с методом `sberbank`.

Администратор заполняет реквизиты получателя, счёт зачисления, `Shop ID` и секретный ключ в `Telegram → Приём оплаты`. Секретный ключ и Telegram-токен API обратно в браузер не возвращает.

Для подтверждения онлайн-платежей зарегистрируйте в кабинете ЮKassa webhook:

```text
https://pay.example.com/api/payments/yookassa/webhook
```

Webhook не доверяет входящему телу: сервер повторно запрашивает платёж у ЮKassa, сверяет ID заявки, пользователя, сервис, сумму и валюту. Зачисление идемпотентно — повторный webhook не создаёт вторую операцию. Если webhook задержался, пользователь может нажать `Проверить` в истории оплат.

Для онлайн-платежей production-домен должен работать по HTTPS, а `PUBLIC_BASE_URL` в env-файле должен совпадать с публичным адресом сайта.

## Проверки

```bash
npm test
npm run build
npm run test:e2e
```

Unit-тесты покрывают календарный биллинг, хеширование паролей, срок сессий и статусы платёжного провайдера. Playwright проверяет flow оплаты, админские реквизиты и отсутствие горизонтальных коллизий на desktop/mobile Chromium. Те же проверки запускаются в GitHub Actions.

## Telegram

Webhook endpoint отображается в разделе Telegram. Для Telegram Bot API его нужно установить как:

```text
https://your-domain.example/api/telegram/webhook/<secret>
```

Пользователю в интерфейсе задаётся Telegram ID. Команда `/pay 600` зачисляет сумму в основной валюте сервиса, конвертирует её в общий RUB-баланс пользователя и не выполняется, если пополнение через бота заблокировано у участника. Команда `/services` показывает все подключённые сервисы пользователя и сколько списывается с него за период. Команда `/users` доступна только администратору бота и показывает пользователей с остатками по сервисам.

В разделе Telegram после сохранения настроек нажмите `Webhook`: приложение зарегистрирует webhook URL и команды `/pay`, `/deposit`, `/balance`, `/services`, `/users`, `/help` в личке бота, а также `/settopic` и `/users` для групп. Для локального `localhost` Telegram не сможет доставлять webhook-события без публичного туннеля или домена.

Если приложение запущено локально или webhook недоступен снаружи, нажмите `Polling`. В этом режиме приложение удалит webhook у Telegram и будет само забирать новые сообщения через `getUpdates`.

Чтобы направить общие уведомления в топик группы, отметьте нужного участника администратором бота в списке пользователей, затем отправьте `/settopic` прямо в нужном Telegram-топике. Бот сохранит `Chat ID` и `Topic ID`; после каждого списания по сервису в этот топик уйдёт список участников с текущими остатками, а уведомления о малом остатке будут пинговать конкретных пользователей там же.
